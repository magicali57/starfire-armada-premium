# Chest Opening — Completion Report

## Scope

Canonical Chest Opening transaction + a polished Chest Vault screen for the three existing chest types (`chestBasic`/`chestRare`/`chestEpic`). No Shop, Daily Rewards, real-money purchases, gameplay changes, Ship Skins, or Companion Rank Up. No rebalance of `CHEST_REWARD_TABLES`.

## Transaction

- **Owner**: `openChestTransaction` in `src/systems/rewards/openChest.ts` — pure state-in/state-out, same shape as `applyCompleteCampaignStage`. Steps: validate chest id → validate ownership → validate the reward table → resolve via `rollDropTable(CHEST_REWARD_TABLES[chestId], randomSource, 1, "chest")` → deduct exactly one chest into a draft state → apply every resolved reward through the existing `applyRewardBundle` (which validates every entry before mutating anything and runs duplicate-collectible conversion through the one existing canonical system) → return one final state + a typed `ChestOpeningResult`.
- **Atomicity/idempotency**: the chest deduction and every reward live in ONE derived `PlayerState` object; on any failure the function returns the pristine ORIGINAL `state` (never the draft), so a bad resolved reward can never leave a chest consumed with nothing granted. There is no separate "apply this result" entry point — a `ChestOpeningResult` cannot itself be replayed; only calling `openChestTransaction` again (a brand-new transaction, fresh `openingId`) can grant anything else.
- **Store wiring** (`store/playerStore.tsx`'s new `openChest` action): a `chestOpenInFlight` ref rejects concurrent calls with a typed `"opening-in-progress"` failure (zero state change). Deliberately stricter than the store's usual best-effort `update()` helper: it calls `persistPlayerState` and only commits to in-memory state (`setPlayer`) if the write succeeds — a disk failure returns `"persistence-failure"` and never touches in-memory state either, so success is never reported for a chest opening the save doesn't actually contain.
- **Randomness**: production calls use `productionRandomSource`; verification uses `createFixedRandomSource`/`createSeededRandomSource`. Nothing in resolution/application/the transaction calls `Math.random` directly (the opaque `openingId` generator does, matching `battleSession.ts`'s `generateBattleSessionId` convention — not reward randomness).

## Route & screen

- Route: `#/inventory/chests` (`chest-opening`), added alongside `loadout`/`companions`/`modules`. Reachable from Inventory Hub's new "Chests" category button and its live chest-count section (`src/data/inventoryHub.ts`, `InventoryHubScreen.tsx`).
- `ChestOpeningScreen.tsx`: Chest Vault grid (art, rarity border, truthful weight-free contents summary from `data/chests.ts`'s `getChestContentsSummary`, owned count, Open/empty state) + a `ModalLayer`-hosted cinematic sequence.
- **Cinematic phases**: `idle → anticipation (480ms) → opening (520ms, light burst) → revealing (650ms, reward rows stagger in) → summary` (interactive: Open Another / Done). SKIP jumps straight to `summary` without rerolling or reapplying anything (all rewards were already committed before the sequence started). Reduced motion skips straight to `summary` on success. Rarity treatment reuses the shared `.motion-glow-rare/epic/legendary` amplitude tiers (Basic→mildest, Rare→stronger, Epic→strongest) tinted via local CSS border/box-shadow colors, per the task's Basic/Rare/Epic glow spec.
- The screen and its cinematic never grant anything themselves — `getChestRevealRows` (`src/data/chestReveal.ts`) only displays what `openChestTransaction` already committed, zipping `resolvedRewards` (pre-conversion, for rarity) with `appliedRewards` (post-duplicate-conversion) to flag genuinely-new collectibles vs. duplicate conversions, reusing `rewardDisplay.ts`'s `toRewardDisplayRows` for aggregation/icons/labels.
